# システム構成・外部連携

## 1. UI技術方針

FastAPI + React/TypeScriptを第一候補とする。

ローカル専用ツールとしてはやや大きい構成だが、HTML、CSSおよびReactが開発者にとって馴染みがあり、今後の工程管理UI拡張も行いやすい。PySide6等のデスクトップGUIを新たに習得するより、既存知識を活用する。

フロントエンドはNext.jsではなく、Vite + React程度の構成とする。

画面はSingle Page Applicationとし、工程ごとのタブを切り替えて利用する。幅1920pxの全画面表示を基本とするが、デスクトップ画面を縦2分割した状態でも主要操作を継続できるよう、一部の表は横スクロールまたはカード表示へ切り替える。

## 2. 想定構成

```text
React / TypeScript
  ↓ HTTP
FastAPI
  ├─ プロジェクトフォルダ操作
  ├─ データセット設定管理
  ├─ バックグラウンドジョブ・キュー管理
  ├─ タグ集計・編集
  ├─ ffmpeg等によるフレーム抽出
  ├─ BandiView起動
  ├─ ComfyUI API連携
  └─ sd-scripts CLI実行

Stability Matrix
  ├─ ComfyUIの導入・更新・起動環境管理
  └─ kohya_ss / sd-scriptsの導入・更新・Python環境管理
```

## 3. 外部ツールとの責務分担

| ツール | 担当 | LoRA Maker側の役割 |
| --- | --- | --- |
| Stability Matrix | ComfyUIおよびkohya_ss / sd-scriptsの導入、更新、Python環境および起動環境の管理 | Stability Matrixが用意した環境を利用する。Stability Matrix自体の更新・画面操作は行わない |
| ComfyUI | 動画生成、画像拡大、自動タグ付け、生成済み動画からの派生版作成 | 素材画像と動画生成プリセットの選択、入力画像とプロンプトの差し替え、処理送信および工程管理 |
| BandiView等 | 動画および画像の人力選別 | 対象フォルダを外部ツールで開く |
| ffmpeg等 | 動画からのフレーム抽出 | 入出力を指定して処理を実行する |
| sd-scripts | LoRA学習の実処理 | 学習設定とデータセットを準備し、Stability Matrix管理下のPython環境からCLI実行し、状態・ログ・成果物を管理する |
| kohya_ss GUI | sd-scripts用の設定作成・手動実行を支援するGUI | 初期版の自動操作対象にはしない。直接実行方式が成立しない場合の確認・代替手段とする |

動画および画像の選別機能はLoRA Makerへ再実装しない。

### 3.1 Stability Matrixとの境界

ComfyUIおよびkohya_ss / sd-scriptsの環境構築とバージョン管理はStability Matrixへ委譲し、LoRA Makerの責務外とする。LoRA MakerはStability Matrixの画面を自動操作せず、パッケージのインストール、更新、起動および停止も初期版では行わない。

ComfyUIは画像・動画生成ワークフローの実行主体として必須依存とする。利用者がStability MatrixからComfyUIを起動し、LoRA Makerは設定されたAPI接続先へ接続する。インストール先の絶対パスはコードへ埋め込まない。

kohya_ssはsd-scriptsを利用するGUIラッパーとして扱う。LoRA Makerからの学習は、Stability Matrixがkohya_ss用に構築したPython環境でsd-scriptsを直接CLI実行する方式を第一候補とする。ただし、Python実行ファイル、sd-scriptsの配置、必要な環境変数、設定受け渡し、終了判定および成果物出力が実機で成立することをフェーズ0で検証してから確定する。

直接実行が成立しない場合は、kohya_ssが生成するコマンドまたは設定ファイルを利用する方式を再検討する。kohya_ss GUIの画面自動操作は、UI変更に弱く保守範囲も広がるため採用しない。

Stability Matrixの標準UIではComfyUIとkohya_ss GUIの同時起動を前提としない。LoRA Makerも両GUIの同時起動を要件とせず、工程ごとに必要な実行基盤を利用する。また、sd-scriptsを直接起動できる場合でも、VRAM競合を避けるためComfyUI生成ジョブとLoRA学習ジョブは同時実行しない。

### 3.2 外部ツール状態の表示

画面の共通領域に、少なくともComfyUI APIの接続状態と、LoRA Makerが開始したsd-scripts学習プロセスの状態を表示する。ComfyUIが停止している場合は必要な工程で「Stability MatrixからComfyUIを起動してください」と案内する。

LoRA Makerは、起動していないkohya_ss GUIを異常とはみなさない。学習可能性はGUIの起動状態ではなく、設定されたPython実行ファイルとsd-scriptsの実行前検証によって判断する。

## 4. ComfyUI動画生成連携

### 4.1 連携単位

動画生成用ComfyUIワークフローは、アプリ全体で共通の1個を管理する。カメラパン、その場で一回転、歩く、しゃがむの違いは、アプリ共通マスタに保持する動画生成プリセットのプロンプトによって表現する。

LoRA Makerは任意のComfyUIワークフローを自動解析する汎用エンジンにはしない。共通ワークフローのプリセットに、画像入力、プロンプト入力および回収対象出力のノードと入力項目を明示する。

1回の要求は、素材画像1枚、動画生成プリセット1個、動画出力1本を単位とする。LoRA Makerは共通ワークフローJSONをメモリ上で複製し、指定された画像入力とプロンプト入力を差し替えてComfyUIへ送信する。保存されている元のワークフローJSONは変更しない。

プリセット選択以外のプロンプト編集、シードその他のノード値を汎用編集する機能は初期実装に含めない。

ComfyUIの動画出力には、LoRA Maker専用の一時出力フォルダを使用する。動画生成処理の前後に同フォルダ配下を空にするため、動画生成要求は直列実行とし、同時実行を禁止する。

### 4.2 前提条件

- ComfyUIが起動しており、API要求を受け付けられること
- 共通ワークフローがAPI用JSONとして実行可能であること
- 共通ワークフローが要求するカスタムノード、モデルおよびその他の依存物がComfyUI側へ導入済みであること
- 共通ワークフロー定義から差し替え対象の画像入力ノードとプロンプト入力ノードを特定できること
- 生成結果を専用一時出力フォルダから`02_動画`へ移動できること

### 4.3 エラー境界

共通ワークフローまたはプリセットの不整合、依存ノード不足、モデル不足、ComfyUI停止、実行時エラーおよび出力回収失敗は、アプリ側で成功扱いにしない。取得可能な範囲でComfyUIのエラー内容を表示する。

動画の品質不良はシステムエラーではない。生成処理が正常終了し、生成動画を`02_動画`へ保存して後処理の削除まで完了した時点で、本アプリ上の動画生成処理は完了とする。

生成された動画は、データセット内・プリセットキー単位の次の連番を採番し、`<プリセットキー>_<3桁連番>.<元の拡張子>`へリネームして`02_動画/<dataset.key>`へ移動する。移動先の保存確認後、専用一時出力フォルダを空にする。

### 4.4 出力フォルダの削除制御

動画生成の前後にファイルを削除するため、削除対象パスは通常のComfyUI出力先と共用せず、LoRA Maker専用として設定する。削除直前には正規化した実パスが設定値と一致すること、および危険な上位ディレクトリを指していないことを検証する。

動画の移動または保存確認に失敗した場合は処理を失敗とし、生成動画を失わないため後処理の削除を中止する。次回実行前の削除については、残存ファイルがあることをログへ記録したうえで実施する。

### 4.5 生成済み動画からの派生版作成

生成済み動画をComfyUIへ読み込んでワークフローを復元し、条件を変更して派生版を作る操作はComfyUIへ委ねる。復元の可否は動画形式、保存ノードおよびメタデータ設定に依存するため、共通ワークフローについて事前確認する。

## 5. バックグラウンド処理と状態管理

動画生成、フレーム抽出、画像拡大、タグ付けおよびLoRA学習等の時間がかかる処理は、Reactのコンポーネント内ではなくFastAPI側で実行状態を管理する。

- タブ移動やブラウザ再読込で実行中処理を中断しない
- ReactはFastAPIから待機中、実行中、完了、失敗等の状態を取得して表示する
- 動画生成要求はキューへ追加し、同時実行数1で直列処理する
- 実行中でも後続要求を待機キューへ追加できる
- キューと処理状態をブラウザのメモリだけに保持しない
- 異常終了後に状態を確認し、再実行を判断できる情報を残す

永続化方式は実装時に決定するが、複数状態の更新と異常終了からの復元を考慮し、JSONを使用する場合は原子的な置換保存を行う。状態遷移や履歴管理が複雑になる場合はSQLiteを使用する。

## 6. BandiView・画像拡大連携

BandiViewは画像の人力選別に使用する。LoRA Makerは対象となる`03_動画キャプチャ/<dataset.key>/<動画名>`を指定してBandiViewを起動する。

BandiViewの画像保存フォルダを複数の処理で共用する場合、異なる選別対象の画像が混在する危険がある。そのため、アプリは選別中の対象を1個だけ管理し、未処理画像が残っている状態で別対象を開始しない。

拡大処理では、BandiViewの画像保存フォルダ内の画像を入力とし、ComfyUIによる拡大結果を`04_拡大/<dataset.key>`へ保存する。保存確認後、同じ画像を`06_LoRA学習素材/<repeats>_<dataset.key>`へコピーする。

BandiViewの画像保存フォルダを空にするのは、拡大、`04_拡大`への保存および`06_LoRA学習素材`へのコピーがすべて成功した後に限る。途中で失敗した場合は入力画像を残す。

## 7. sd-scripts・kohya_ss・modelsフォルダ連携

LoRA学習時は、`06_LoRA学習素材`をsd-scriptsのデータセットとして指定する。各データセットフォルダは`<repeats>_<dataset.key>`形式とし、識別タグはフォルダ名ではなくキャプションへ保存する。

LoRA Makerは学習設定を生成または選択し、設定されたPython実行ファイルからsd-scriptsの対象スクリプトを子プロセスとして起動する。作業ディレクトリ、引数、環境変数、標準出力、標準エラー、終了コードおよび成果物出力先を記録する。Stability Matrix管理下のファイル配置は更新によって変わり得るため、実行パスはアプリ個人設定で指定し、起動前に存在と実行可能性を検証する。

学習開始前には、ComfyUIの生成ジョブおよび他の学習ジョブが実行中でないことを確認する。ComfyUI APIが接続中の場合にサーバー停止まで必須とするかは、実機のVRAM使用量を確認して決めるが、初期運用では停止を推奨し、同時にGPU処理を流さない。

学習結果は`07_LoRA`へ保存する。ComfyUI等のmodelsフォルダへ配置する場合はコピーとし、`07_LoRA`の原本を維持する。modelsフォルダから削除する場合も配置先コピーだけを対象とする。

同名ファイルが存在する場合はファイルサイズまたはハッシュ等で同一性を確認し、内容が異なるファイルの上書きまたは削除は明示的な確認対象とする。

## 8. 開発時の起動方式

開発中はFastAPIとVite開発サーバーを別々に起動してよい。

### 8.1 開発環境の固定バージョン

開発開始時点である2026-09-17の安定最新版を基準とし、次のバージョンを使用する。

| 対象 | 固定バージョン | 備考 |
| --- | --- | --- |
| Python | 3.14.7 | 実行環境を固定する |
| Node.js | 26.9.0 | Current安定版を採用する。LTSへの切り替えは行わない |
| npm | 11.19.1 | JavaScriptパッケージ管理に使用する |
| FastAPI | 0.141.1 | Python依存パッケージとして完全固定する |
| Pydantic | 2.13.5 | beta版は採用しない |
| React | 19.3.0 | フロントエンド依存パッケージとして完全固定する |
| Vite | 8.3.0 | 開発サーバーおよびビルドに使用する |

JavaScriptパッケージ管理にはnpmを使用し、pnpmは使用しない。

### 8.2 バージョン管理方針

- `package.json`では主要パッケージを`^`や`~`による範囲指定にせず、完全一致で指定する
- `package-lock.json`をGit管理し、環境再構築時は原則として`npm ci`を使用する
- Pythonランタイムのバージョンを`.python-version`等で明示する
- FastAPIおよびPydanticを含むPython依存パッケージは、`requirements.txt`または採用するPythonパッケージ管理方式のロックファイルで完全固定する
- 開発中に新しい安定版が公開されても自動追従しない
- バージョン更新は、必要性、互換性および既存機能への影響を確認したうえで明示的に実施する
- 上記以外の直接依存パッケージも、初期実装で採用した時点のバージョンに固定する

### 8.3 技術選定の寿命に関する方針

本アプリは長期保守性より、開発時点のAI画像生成環境およびLoRA制作工程への適合を優先する。Node.jsについてもLTSではなく、開発開始時点のCurrent安定版を採用する。

数年後まで同一構成の後方互換性を維持することは目標としない。生成AI技術、ComfyUIワークフローまたはLoRA制作工程が大幅に変化した場合は、古い依存関係を延命するのではなく、必要に応じてアプリ構成自体を見直す。

ただし、開発期間中の再現性は必要であるため、「開発開始時には安定最新版を採用し、採用後は固定する」方針とする。

## 9. 完成後の起動・配布方式

Reactをビルドし、FastAPIから静的ファイルとして配信する。Python側の起動だけで利用できる構成とする。

### 9.1 Chrome自動起動

Pythonプログラム起動時にGoogle Chromeを起動し、FastAPIのトップページを開く。

- 使用するChromeプロファイルは`Default`で固定する
- FastAPIの待受開始を確認してからChromeを起動する
- 起動対象URLはFastAPIのトップページとする
- Chrome起動に失敗した場合はエラーをログへ記録し、ブラウザ接続待機の終了条件に従う

### 9.2 ブラウザ接続監視

ブラウザとFastAPI間はServer-Sent Events（SSE）接続を確立し、接続中のブラウザウィンドウ数をPython側で管理する。

ここでいう接続ウィンドウ数は、LoRA Makerのトップページから確立された有効なSSE接続数とする。SSE切断時は接続数を減算し、再接続時は新しい接続として加算する。ブラウザ再読込や一時的なSSE再接続による瞬間的な0件判定で即時終了しないよう、終了判定には起動後10秒の猶予時間を設ける。

### 9.3 自動終了条件

Pythonプログラムの起動から10秒経過した時点以降、SSE接続数が0になった場合は終了要求状態へ移行する。実際にFastAPI/Pythonプロセスを終了するのは、実行中ジョブと待機中ジョブがともに0件になった時点とする。

実際の終了条件は次のすべてを満たすこととする。

- Pythonプログラムの起動から10秒以上経過している
- SSE接続数が0である
- 実行中ジョブが0件である
- 待機中ジョブが0件である

終了制御は以下の通りとする。

- 起動後10秒未満は、SSE接続数が0でも終了要求状態へ移行しない
- 起動後10秒経過時点でSSE接続数が0かつジョブが存在しない場合は終了する
- 10秒経過後に最後のSSE接続が切断された場合、ジョブが存在しなければ終了し、ジョブが存在する場合は終了要求状態へ移行する
- 終了要求状態では、すでに待機中または実行中のジョブを途中終了させず、待機キューを最後まで消化する
- 実行中ジョブおよび待機中ジョブがすべて完了した時点でSSE接続数が0なら終了する
- 終了要求状態の間にブラウザが再接続し、SSE接続数が1以上になった場合は終了要求状態を解除して通常稼働へ戻る
- 終了時は新規要求の受付を停止し、可能な範囲でログのflush等の終了処理を行ってからFastAPI/Pythonプロセスを終了する

この方式により、ブラウザを閉じても動画生成、画像拡大、タグ付け、LoRA学習等の処理は完了まで継続し、処理完了後にブラウザ接続がなければアプリ全体を自動終了する。

### 9.4 注意点

SSE接続数は「Chromeプロセス数」や「OS上のウィンドウ数」そのものではなく、LoRA Makerへ接続しているブラウザ画面数を近似するための値である。Chromeの別タブ、バックグラウンド化、クラッシュ、ネットワーク断等によってSSEは切断・再接続されるため、実装では接続カウンタの二重減算やリークを防ぐ。

Chrome自体のプロセス終了監視は必須とせず、SSE接続の有無をアプリ利用継続の判定基準とする。

将来、よりデスクトップアプリらしい形が必要になった場合は、pywebview等を外側に被せることを検討する。
